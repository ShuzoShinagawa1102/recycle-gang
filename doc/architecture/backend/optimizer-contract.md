# 最適化サービスとの連携契約案

更新日：2026-10-03。責務分離・入力スナップショット方式は合意済み。以下は契約具体化のたたき台。

## 通信と所有

Spring Bootが計算対象を決め、同一時点の入力を作成してFastAPIへ渡す。Pythonは経路候補を返す。業務計画としての採用・割当・保存・業者への提示はSpring Bootが行う。

最適化結果は候補であり、数学的な最適性を常に保証するものではない。時間上限内の実行可能解、実行不能、時間切れ、部分割当を区別する。移動時間/距離行列の提供元は未決で、直線距離を実際の走行時間として扱わない。

## 入出力の最小候補

| 区分 | 項目例 | 用途 |
|---|---|---|
| 識別 | requestId、snapshotId、planningScopeId、planningRevision | 再送、入力版、結果照合 |
| 訪問 | 予約/訪問ID、座標、時間窓、作業時間、積載量、優先条件 | 計算制約 |
| 車両 | 車両ID、開始/終了地点、稼働時間、容量 | 利用可能資源 |
| 計算条件 | constraintVersion、matrixVersion、timeLimit、solver設定版 | 再現性、比較 |
| 結果 | status、車両別訪問順、到着見込み、距離/時間、未割当と理由 | 採用判定と業者提示 |
| 証跡 | 入力ハッシュ、solverVersion、計算時間、警告 | 不具合再現 |

氏名・電話番号・決済情報は渡さない。住所を座標へ変換する処理の所在と利用規約は地図サービス選定時に決める。業務上の非公開なオファー上限式も計算に不要なら送らない。

## 計算中の予約変更への対応

1. 基幹が短いトランザクションで対象予約・資源・制約の整合したスナップショットを保存する。
2. DBトランザクションを終了してからHTTPで計算要求する。計算時間中に業務行のロックを保持しない。
3. 計画に影響する予約変更、取消、車両/稼働条件変更、割当変更では、その計画範囲のrevisionを同一更新トランザクションで進める。
4. 結果受領時にrequestId、入力ハッシュ、制約充足、訪問の重複/欠落、権限・状態を確認する。
5. 候補採用トランザクションで現在のrevisionと入力revisionを比較し、計画更新と一体で排他する。比較後に競合更新が入り込む構成を避ける。
6. 不一致なら候補をstaleとして記録し、再計算または運営判断へ進める。古い候補で予約や割当を上書きしない。

revisionの範囲を便/地域/日付のどれにするかは集約設計で確定する。関連する全変更を捕捉することが必要で、予約のupdatedAtだけの比較では不十分。複数範囲にまたがる計画はrevisionの組または同等の整合性検証を使う。

## 同期／非同期

小さい入力で計算上限がHTTPの制限内に収まる間は同期RESTで開始可能。計算制限・タイムアウト・失敗時応答を明記する。

長時間化した場合は`POST /v1/optimization-jobs`で202とjobId、`GET /v1/optimization-jobs/{id}`で状態/結果を返す案とする。ジョブ状態は永続化し、重い計算は別プロセス/ワーカーで実行する。FastAPIのasyncやBackgroundTasksだけで耐障害性が得られると考えない。

同じrequestIdで同じ入力が再送されたら同じジョブ/結果を返す。異なる入力なら競合として拒否する。採用は基幹側でも一度だけ行う。再試行上限、保持期間、キャンセル、再起動復旧、solverの同時実行数は非同期実装時に必須とする。
